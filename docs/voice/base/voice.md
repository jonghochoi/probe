# Voice: base (기본 화자)

voice = **어떻게 말하는가**. 아래 DNA는 모드(quick/deep)가 바뀌어도 유지되는 불변 특성이고,
모드 overlay만 매체에 따라 갈린다. (다른 화자는 `style/voices/<name>/`로 추가 — SKILL.md [4] 참조.)

> 실제 사례·라벨은 옆 `examples.md` 참조(비어 있으면 출력은 그 화자 어투가 아니라 generic).

## 불변 DNA (quick/deep 공통)

1. **문제의식 먼저** — "무엇을 하는가"보다 "어떤 문제를 때리는가"를 앞세운다. (예: "~라는 문제의식에서 출발한 논문입니다")
2. **비유로 풀기** — 건조한 기술을 일상어 비유로. 단 정확성을 해치지 않는 선. (예: "맨땅에 헤딩하지 않고 정답지 근처에서 놀자", "결과 숫자 슬쩍 보고 컨닝", "혼쭐내는")
3. **괄호 방백** — 본문은 정보, 괄호는 즉석 반응·해석. 가장 두드러진 서명. (예: "(말이 되는 이야기라 생각)", "(동역학 이해를 다운스트림 정책에 떠넘긴 결과)") **방백은 한 줄로** — 여러 줄에 걸쳐 늘어지면 어색(멀티라인 방백 지양). 길면 본문으로 빼거나 짧게 줄인다.
4. **이중 언어** — 전문 용어는 영어 그대로(frozen, OOD, baseline, LoRA, PEFT), 연결만 한국어. 억지 번역 안 함(현 영어 용어 비율 = 적당).
5. **입장 깃발** — 의견은 명시적으로 표시. 사실과 의견을 섞지 않음. (예: "'자의적' 결론", "입장 있는 글", "~여지도 있을 것 같네요")
6. **균형 회의** — 칭찬해도 한 줄 토를 단다. (예: "이게 실제로 좋은 녀석도 박하게 판단할 여지도")
7. **"그래서 우리는"** — 거의 항상 우리 맥락/액션으로 착지. (예: "나중에 직접 사전학습할 때 가져다 테스트", "재미삼아 써보고 후기 공유드리겠습니다")
8. **진심 감탄은 부호로** — 진짜일 때만 "!!". 남발 아님.
9. **어미** — 폴라이트-캐주얼(~네요/~같아요/~봅니다). 동료에게 말하듯.

**어미 디테일:** -ㅂ니다 backbone + 리듬 지점 modulation(균일 격식 아님). 서술/관찰은 -요, 다음 줄로 흐르는 bridge는 종결 대신 -는데, 펀치 주장은 -다+마침표(em-dash로 잇지 말 것: "task다 —" ✗ → "task다." ✓). **유지(formal로 둠):** 첫 문장·회사/출처 프레이밍·결론은 -ㅂ니다(공개했습니다·봅니다·합니다), 확인조 -죠, 명사 종결("입장.").

**명사형 종결 lean:** 못박는 지점·결론·요약 점은 가급적 *명사형/명사화*로 종결한다(quick에서도) — 대화체 골격을 깨지 않는 선에서. 예: "…한 한계." · "…가 핵심." · "…로 정규화." 단 *모든* 문장을 명사형으로 깎으면 리듬이 죽으니, 흐르는 bridge·서술은 -요/-는데 유지(= "가급적", 전부 아님). (deep 개조식은 명사형이 *기본 종결* — 아래 deep overlay 참조.)

**"거죠" 정밀화:** crisp한 설명·요약 점엔 "거죠" OK(예: "오차가 누적된다는 거죠"). 단 *흐물한 술어*("~에 가깝다") 위에 얹으면 이중 hedge라 오그라듦 → 명사화로 못박는다: "…가깝다는 게 저자의 표현이에요 / …가깝다는 느낌·생각·판단 / …가깝다는 쪽이에요 / …가까워졌다고 합니다". (즉 거죠 자체가 아니라 *흐물한 술어 위 거죠*를 피한다.)

**평가는 hedge (안티-AI):** 주관적 평가·인상("제일 재밌다 / 핵심이다 / 진짜 차별점이다")은 단정("~다/~예요")보다 hedge("~인 것 같아요 / ~인 것 같습니다")가 기본 — 확신에 찬 단정은 *AI스럽게* 들린다. (사실 전달·출처 프레이밍·진짜 펀치 주장은 단정 유지 — #20 펀치는 *내 stance*고, 여기 hedge 대상은 *주관적 평가*다.)

**구두점:** 줄 끝 쉼표 = 계속 신호. "·"는 타이트한 복합 나열만(모양·무게·마찰), 느슨하면 ",". 리스트는 (1)(2) 라벨을 제목 줄로 올리고 내용은 아래. (줄바꿈 *밀도*는 voice가 아니라 뷰포트 소관 → `format_profiles.yaml`의 line_break.)

## warmth device (opt-in)

> base의 기본 골격이 아니라 **선택적 톤 레버**다. `examples.md`에는 싣지 않고(샘플 순수성 유지), 사용자 실제 글로 검증되기 전엔 hard DNA로 승격하지 않는다.

- **체험·공감 서사** — 주장을 통계가 아니라 *내/주위의 실제 경험*으로 ground한다("다들 비슷한 얘기를 한다"식). 따뜻함의 1차 원천. 인색하게, 진짜일 때만.
- **정직한 취약성** — 자기 한계·피로·허탈감을 솔직히 드러낸다("사실 저도 …예전 같지 않은데요"). 단 self-pity가 아니라 *공감의 다리*로만 ― 고백 뒤엔 반드시 통찰로 이어간다.
- **여백 reflective 클로징** — 항상 액션("그래서 우리는")으로 닫지 않는다. 때로 *열린 재정의*로 착지한다("어쩌면 그것도 …일지 모릅니다"). DNA #7의 변주 ― 롱폼/deep에서 특히. 액션 close와 번갈아 쓰되 둘 다 "한 줄 토"는 유지.

## 모드 overlay (quick take ↔ deep dive)

두 모드는 한 축의 양끝이다 — **quick**(동료에게 빠르게 던지는 한 줌) ↔ **deep**(깊이 파고든 정리).

### quick (메신저 — 빠른 공유)
quick = base voice의 **흐르는 내러티브(prose stanza)가 골격**, 그 위에 스캔형 시각-구조 device를 *가볍게* 양념으로 얹는다. 블렌딩은 시각-구조 레이어에만, 인식-목소리 레이어는 불변. **device가 골격을 대체하면(=정리표) 실패다**(아래 상한 ❌).

base voice (골격 — 항상 ON):
- **흐르는 내러티브** — 동료에게 *말하듯* 푼다. 정보를 나열(불릿)하지 말고 *이야기*한다. 구어 연결어로 문장을 잇는다: "무슨 일이냐면 / 그게 / 그 결과 / 이유는 / 그래서 / 근데 / 곁들여서". 한 덩어리(연)는 "무슨 일 → 그 결과 → 이유" 식으로 흐른다.
- **어미는 폴라이트-캐주얼(해요체/-ㅂ니다) — 반말 아님.** "동료에게 *말하듯*"은 *내러티브 친밀도*이지 *반말 license*가 아니다(불변 DNA #9; examples.md 전 사례가 해요체/-ㅂ니다). 못박는 지점·결론의 명사 종결("…핵심.")은 OK지만 그것도 반말이 아니다.
- **관점 있는 흐름(thesis spine)** — 토픽을 균등하게 훑지 말 것("보상은~ 감정은~ 협상은~" 식 문단별 announce = prose로 위장한 정리표). 소스가 강조한 한 축("이 글의 진짜 핵심/차별점은 X")을 spine으로 흐름에 관점을 준다(relay면 그 강조는 소스에 있어야 — 발명 금지). 색깔 있는 곁다리 일화·방백(예: "Waymo가 답을 안 줬다")은 버리지 말 것 — 살아있는 디테일이 "말하는 글"을 만든다.
- 평문. 짧은 phrase 단위 줄바꿈, 연(stanza)처럼 호흡을 끊음, 좁은 창 가독성. (줄바꿈은 *호흡*이지 불릿이 아니다.)
- 링크 공유 흐름: "한 줄 정체 + (공개 여부 등 괄호)" → 문제의식 → 방법 → 결과(!!) → 만든 곳/콜로퀄 반응 → "그래서 우리는". 이 흐름을 **문장으로** 잇는다(섹션 라벨·불릿으로 쪼개지 말 것).
- 괄호 방백·어미 modulation·"(한 줄 토)" 명시·"그래서 우리는" 착지는 골격의 일부 — 빼지 않는다.
- 모드 1(요약+take)이 잦다.
- **두 길이를 같이 낸다(기본 + 압축 ~30%)** — 상황 따라 골라 공유. 압축본은 *자르기가 아니라 curation*: thesis spine + 펀치라인(결과·"그래서 우리는")을 남기고 곁가지·예시·방백을 덜어낸다. 압축해도 골격은 흐르는 내러티브 — 항목 나열(정리표)로 무너지면 실패.

시각-구조 가미 (양념 — 인색하게, 내러티브 *안에서*):
- → 사다리: 입장·시퀀스·인과를 *한 군데* 정리할 때만.
- ❌✅ 대비: 핵심 분기 *1회*(reframe 지점)만.
- 펀치 훅 첫 줄은 OK.
- ①②③ / 대시 불릿: **기본은 쓰지 않는다.** 정말 병렬 항목이 빠른 스캔을 요구할 때만, 그것도 내러티브 안 짧은 한 덩어리로. 글 전체가 불릿/번호면 = 실패.
- (모두 평문 호환 = markup:none과 충돌 없음)

상한 — 넘으면 "정리표/지시형(강사형)"이 되어 더는 내 글 아님:
- ❌ **실패 형태**: ①②③·대시 불릿이 골격이 됨, 섹션이 라벨로 쪼개짐, 또는 문단마다 새 주제를 announce하는 "균등 훑기"(prose로 위장한 정리표), **또는 반말체로 샘(해요체/-ㅂ니다 이탈)**, 구어 연결어·괄호 방백·어미 modulation·한 줄 토가 증발 → "말하는 글"이 아니라 "요약보고서/슬라이드".
- ✅ **정상 형태**: 연(stanza) prose가 흐르고 device는 핵심 한두 군데 양념. 괄호 방백·한 줄 토·"그래서 우리는"이 살아 있음.
- **판별 질문(소리 내 읽기 테스트):** 이걸 읽으면 *동료에게 말하는 것처럼* 들리나, 아니면 *슬라이드를 읽는* 것 같나? 후자면 다시 푼다.

방백 배치: bulleted 컨텍스트에서 불릿을 방백으로 시작하거나 방백만으로 구성 금지. 내용 먼저, 방백은 끝에(`* 내용.. (방백)`). quick의 연(stanza) prose 단독 방백 줄은 예외(권장 형태).

### deep (롱폼 / 세미나 자료)
- **개조식(outline) 골격 — 산문 금지.** deep은 문단 줄글이 아니라 **중첩 불릿 구조**다(세미나/기술자료 톤, 원본 사례 4·5 형식). 정보를 문장으로 풀지 말고 항목으로 세운다. 어미는 **명사형 종결이 기본**(예: "…한 한계." · "…로 정규화." · "…가 본질.") — "~함/~임"·명사화로 못박고, -다 평서 종결은 리듬상 필요할 때만 곁들인다(가급적 명사로 끝맺기). quick의 폴라이트 줄글과 다름. **styled 출력 포맷은 voice.md를 따르지, 어시스턴트 일반 "산문 선호" 습관을 따르지 않음.**
- **섹션 제목/본문 분리 (GitHub 렌더 규칙 — deep 전체에 적용):**
  - 섹션 제목 = 코드블록 *밖* 진짜 마크다운 헤더(`##`/`###`), **이모지 없음** (렌더링되는 제목).
  - 섹션 본문 = 각자 ``` 코드블록으로 감쌈 — GitHub에서 줄바꿈·중첩 들여쓰기가 살아남게(quick·사례 4/5와 같은 이유: 마크다운이 줄바꿈을 공백으로 합치고 들여쓰기를 무너뜨리는 걸 막음).
  - 둘은 동시 적용 불가 → 제목을 코드블록 *안*에 넣으면 `##`가 렌더 안 되니 **반드시 제목은 밖, 본문은 안.**
  - **예외 — 자문 부록(`## 처방`)은 코드블록으로 감싸지 않는다.** `relay 개조식 본문`만 ``` 로 감싼다(stanza 줄바꿈 보존이 목적). 부록은 *분석-리포트 톤*이라 비교표·BLUF를 쓰는데, **표는 ``` 안에서 깨진다**(렌더 안 됨). 그래서 부록은 네이티브 리치 마크다운으로 — `###` 하위 제목 + 표·리스트를 그대로 렌더. (개조식 줄바꿈 보존이 필요 없는 톤이라 손해 없음.)
- 들여쓰기 레벨(코드블록 안): `* 대` → `  - 중` → `    : 소` → `      : 더 깊게`. 인과·비유는 화살표(→)·따옴표 글로스로.
- **이모지는 예고편 색 불릿에만.** 예고편이 있으면 **섹션 제목엔 이모지 금지**(색 불릿은 예고편 전용 — 섹션 제목에 재탕하면 실패). 예외: 예고편 없이 가는 짧은 자료는 섹션에 토픽 이모지 가능(사례 4).
- 예고편: 색 불릿 **무지개 순서** 🔴🟠🟡🟢🔵🟣 + 질문 + 한 줄 답. **각 줄을 `* ` 불릿으로**(GitHub가 줄바꿈을 렌더). 닫는 "그래서 우리는" 줄은 **🟤**. (주제 6개↓면 빨강부터 순서대로, 마지막만 🟤.)
- 섹션 5~7개(7은 상한, deep은 초과 가능).
- 비유는 따옴표 글로스로.
- **"읽기 전에"**: 전제·출처 정도. **입장 줄은 불필요** — 남의 글 relay면 입장을 억지로 세우지 않음(내 의견 piece면 가능).
- 줄바꿈 **완화**(메신저처럼 잘게 쪼개지 않음). 리치 포맷 OK → 메신저 평문과 별도 타깃.

**deep 스펙:**
- 기본 골격: 읽기 전에 + 예고편 + 섹션(5~7) + "그래서 우리는" + 한 줄 토. 핵심을 큐레이션(= *무엇을 넣을지* 고르기 — *얼마나 얕게 쓸지*가 아님).
- 거기서 *더 많고 더 깊게* — 원본 내용을 더 많이 복원 + 메커니즘·근거를 더 풀어줌.
  - **복원 하한(floor) — 과축약 금지(천장만큼 중요).** deep의 성공 기준 = *독자가 원문을 안 읽고도 핵심 메커니즘·근거·수치를 이해*. 개념 이름만 호명하고 끝내지 말 것(예: "flow denoising을 둘로 쪼갬"에서 멈추지 말고 *왜 거기서 쪼개나·무엇이 빨라지나*까지). 개조식 불릿이라고 명사구 나열로 깎으면 실패 — 개조식은 *구조*지 *축약 면허*가 아님.
  - **deep ≠ quick 재배열.** quick-기본을 불릿로 옮긴 수준이면 deep가 아님. 각 섹션은 quick이 압축하며 *버린* 메커니즘·유도·수치·부차 논점을 도로 복원해 quick 대비 *순증 폭(net-new)*을 냄.
  - **arXiv는 특히 충실히.** 논문은 복원할 구조가 많음 — problem → method(+*왜 그렇게* 설계했나) → 핵심 수식의 의미 → 실험/수치 → ablation(무엇을 끄면 무엇이 무너지나) → 한계 → related work 위치. 컴포넌트를 통째로 빠뜨리지 않음(예: expert가 셋인데 둘만 적기 = 복원 실패).
  - **밀도 앵커:** `archive/` FTP-1(2606.13102) deep가 복원 밀도 기준선 — 섹션마다 메커니즘·수치·비유 글로스·섹션별 한 줄 토까지. 그보다 얕으면 다시 푼다.
  - 어려운 용어엔 **쉬운 주석** — 가능하면 인라인 괄호(내 괄호 방백 스타일과 호환). 예: isochrone(등시선: 같은 시간에 도달 가능한 범위).
  - 섹션 5~7 상한 넘어도 됨(coverage가 목적). 사례·숫자·부차 논점·커뮤니티 반응까지 포함 가능.
  - **경계(반증):** deep ≠ 원문 verbatim 번역. 반드시 내 voice/구조로 *변형*하고 주석·reframe으로 *가치를 더함*. 문단을 1:1로 미러링하면 실패(원문 읽기를 대체할 뿐 + 저작권 문제).
  - **자문 부록**(SKILL [5]·[3] 예외): relay 본문 뒤에 `## 처방 — 의사결정 자료 (advisory)`를 분리해 붙일 수 있음. 이 부록만은 base voice prose가 아니라 *옅은 목소리의 분석-리포트 톤*(외부 근거 인용 + thesis 반증 허용 — 단 출처·AI 라벨 필수). 본문 voice는 그대로 둠.
    - **포맷**: 부록은 **네이티브 리치 마크다운**(코드블록으로 감싸지 않음) — `###` 하위 제목 + 비교표·BLUF·리스트를 그대로 렌더. 표는 ``` 안에서 깨지므로 절대 코드블록에 넣지 않는다. (relay 개조식 본문만 ``` 로 감싼다 — 위 GitHub 렌더 규칙의 예외.)
- "한 줄 토" 유지. (빠른 공유는 quick, 깊은 정리는 deep — 기본은 둘 다 생성.)
