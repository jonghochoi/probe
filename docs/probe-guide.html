PROBE
Research Scout for Dexterous Manipulation

arXiv에 매일 50 ~ 100편이 올라옵니다. 그 중 당신이 다음 주 학습·평가 파이프라인에서 바꿔야 할 3 ~ 5편만을 찾아오는 자동 스카우트.
"It doesn't read papers. It scouts them."

Python 3.10+ arXiv REST Semantic Scholar Graph Claude Code Routines MIT License
빠른 시작 → 파이프라인 보기

왜 PROBE인가?

로보틱스 연구자의 하루는 이미 빡빡합니다. 모델을 학습시키고, 하드웨어를 디버깅하고, 결과를 분석하다 보면 arXiv는 자연스럽게 뒤로 밀립니다. 문제는 cs.RO + cs.LG에 매일 50 ~ 100편이 새로 올라온다는 것입니다. 그 중 Hand-centric dexterous manipulation + Sim-to-Real에 실제로 연관된 논문은 주당 3 ~ 5편 — 3 ~ 5% 신호율입니다.

직접 필터링하면 매주 몇 시간이 사라집니다. 포기하면 누군가 이미 풀어 놓은 문제를 다시 풉니다. PROBE는 그 3 ~ 5%를 대신 찾아오고 — 다운로드 폴더에서 죽게 두지 않습니다. 단순 요약 대신 두 갈래로 의사결정 재료를 만듭니다 — outward (찾기), focused (깊이 읽기):

🎯

"이 논문이 흥미롭다"가 아니라 "이 논문이 맞다면 다음 주 내 학습·평가 파이프라인에서 무엇을 바꿔야 하는가"를 묻습니다.

❌ PROBE 없이
📅 "주말에 arXiv 한번 봐야지" → 결국 안 본다
🌊 매일 50 ~ 100편 → 제목만 훑고 잊는다
📖 survey 모드: "이거 흥미롭네"에서 끝
🔁 이미 출판된 해를 한 주 내내 다시 푼다
🔊 echo chamber — 같은 저자, 같은 방법론
🌫️ 핀된 논문이 6주 뒤엔 흐릿한 노이즈가 된다
📚 "이 논문 제대로 읽어야지" → 영영 안 읽는다
🗂️ "같은 주제 논문끼리 뭐가 엇갈리는지 정리가 안 된다"
✅ PROBE와 함께
📥 정기 Scouting Report가 레포에 commit 된다
🥇 3 ~ 5편 / 주 — scored, 너의 open question에 묶여 있음
⚙️ decision 모드: "DR object_mass를 [0.5, 2.0] kg로"
🧭 citation graph가 prior art를 먼저 보여준다
🌱 주기적 cross-pollination — 인접 분야에서 강제 1편
🔬 /analyze-paper가 Decision Log에 묶인 한글 deep-dive를 만든다
🧪 /hypothesize가 누적 DB를 가로질러 반증가능한 가설을 뽑는다

요약 vs 의사결정

📰

요약 (cheap)

"이 논문은 contact-rich manipulation에 대한 새 방법론을 제안합니다." — 100편 읽어도 다음 행동이 안 바뀝니다.

⚙️

의사결정 (decision-grade)

"P2 D-7 reach baseline의 reward shaping에서 contact penalty 계수를 0.1 → 0.03으로." — 직접 다음 주에 바꿀 한 줄을 만듭니다.

파이프라인 — 두 갈래 + 합성 사이드카

PROBE는 하나의 정적 컨텍스트를 공유하는 두 갈래의 산출물입니다 — outward (scouting/), focused (analysis/) — 여기에 누적된 analysis/ DB를 거꾸로 가로질러 읽는 읽기 전용 합성 사이드카(hypotheses/, /hypothesize)가 더해집니다. 각 갈래는 서로 다른 질문에 답하고, 서로 다른 주기로 돌며, 자기 폴더에 씁니다.

OUTWARD

Scheduled Scouting
  • 정해진 주기로 정기 실행, pillar 별
  • · Citation-Graph 확장
  • · Keyword Sweep
  • · Curated-List Sweep
  • · 0–3 점수 + decision implication
scouting/P#/YYYY-MM-DD.md 3 ~ 5편 / 실행, append-only, 한글

FOCUSED

On-demand Analysis
  • 슬래시 커맨드 호출 시
  • · /analyze-paper <id|url|pdf>
  • · full-text 우선 (arxiv/html → ar5iv → abstract)
  • · 중립 요약 + decision-grade 함의
  • · P#/D# 앵커 + 컨텍스트 제안
analysis/<id>/analysis.md 한글 deep-dive, 덮어쓰기

사이드카: hypothesize (read-only 합성)

/analyze-paper가 한 편을 깊이 판다면, /hypothesize <P0..P5 | D# | D#-D#>는 이미 쌓인 analysis/<id>/ deep-dive 들을 한 pillar/decision 범위로 가로질러 읽어, 인간 소유 Decision Log(D1–D32)에 대한 tension 을 채굴하고 순위화·반증가능한 가설 + 합의·불일치 매트릭스를 hypotheses/<slug>/에 남깁니다. 실험은 실행하지 않습니다 — 산출물은 검증된 결론이 아니라 test-ready 실험 명세이며, 모든 가설은 inferred/unverified 라벨로 출하(경험적 검증은 사람 몫). --seed "<아이디어>"로 사용자 가설을 top-down 주입할 수 있습니다. 사전조건: 범위에 묶인 분석 ≥3편.

핵심 원칙 — 정적 vs 동적, 절대로 섞지 않는다

context/(정적)와 산출물 트랙들(동적) 사이의 분리는 단 하나의 이유로 존재합니다 — 에이전트 컨텍스트를 가볍게 유지하기 위해서입니다.

📌
정적 (context/) — 월 단위로 한 번 정도 바뀐다
에이전트는 읽기만 합니다. 절대 쓰지 않습니다. MASTER.md(글로벌 앵커 — 여섯 pillar(P0–P5) 개요·cross-cutting) + P{0..5}.md(pillar별 Decision Log·Tracked Literature 등 소유). 클라우드 루틴은 P#.md 하나만 읽어 컨텍스트를 가볍고 pillar-focused 하게 유지합니다.
✍️
동적 — 에이전트가 쓴다
scouting/는 append-only(실행마다 pillar별 새 dated 파일 1개; 다음 실행은 해당 pillar의 직전 ~2주분만 읽음). analysis/는 매 실행마다 덮어쓰는 living snapshot — 이력 없음, 필요 시 재생성.
🚫
절대 섞지 않는다
모든 것을 한 파일에 쌓으면 몇 주 안에 컨텍스트가 부풀어 에이전트가 이미 다뤘던 논문을 재추천하거나, pinned literature가 망각됩니다. pillar 내용은 해당 P#.md를, cross-cutting 내용은 MASTER.md를 편집하세요.

빠른 시작 — 3단계 점진적 자동화

당신은 단계를 건너뛰지 않습니다. Stage 1에서 살아남은 프롬프트가 Stage 3에 배포되는 프롬프트입니다. 자동화 → 나쁜 프롬프트 → 주기적으로 쓰레기 로그 자동 생성. 1 ~ 2주 수동 실행으로 품질을 잡은 뒤 Routine에 올립니다.

1

Stage 1 — 수동 실행 (Week 1–2)

새 Claude.ai 대화 → 해당 context/P#.md 업로드 → Scouting Prompt 붙여넣기(실행 날짜 + pillar 채우기) → 결과를 scouting/templates/report.md 기준으로 검토. 통과하지 못하면 모델이 아니라 프롬프트가 문제입니다. scouting/P#/YYYY-MM-DD.md로 저장 후 commit. 정해진 주기로 반복.

2

Stage 2 — 반자동화 (Week 3–4)

Claude Desktop → Settings → Scheduled Tasks. 트리거: 정해진 주기로 09:00 Asia/Seoul 정기 실행. 프롬프트는 Stage 1과 동일. 한 달이면 충분히 가치 있지만, 노트북이 깨어 있고 데스크톱 앱이 떠 있어야 한다는 한계.

3

Stage 3 — 완전 자동화 (Week 5+)

Claude Code Routines RemoteTrigger 폼에 .claude/prompts/scouting.txt 전문을 붙여넣되, 사전에 템플릿의 <PILLAR> 토큰을 대상 pillar(P0/P1/P2/P3/P4/P5) 로 1회 find/replace 해 두고, 레포·스케줄·환경을 지정. 단일 템플릿이 6개 pillar 루틴에 공유되므로 prompt 로직 수정은 한 파일만 고치면 됩니다(폼은 6개 모두 재붙여넣기). 클라우드 루틴은 로컬 MCP 서버에 도달할 수 없으므로 검색은 curl REST(arXiv + Semantic Scholar Graph)로만 수행. 환경의 Network access = Custom으로 export.arxiv.org / arxiv.org / api.semanticscholar.org 세 도메인을 허용해야 합니다. 산출물은 자체 commit + push 후 PR로 열립니다.

⚠️

두 가지 403을 혼동하지 마세요. x-deny-reason: host_not_allowed은 네트워크 정책(Custom 허용 도메인 누락) — Step 1에서 해결. Semantic Scholar 403은 키 인증 실패 — 무효한 키를 가지고 있다면 환경변수에서 제거하고 keyless로 운영(200 OK).

Week 1–2:  수동 실행     새 대화 → context.md 업로드 → 프롬프트 실행
Week 3–4:  반자동화      Claude Desktop Scheduled Tasks (데스크톱 앱 오픈 시)
Week 5+:   완전 자동화   Claude Code Routines (클라우드, 노트북 꺼도 실행)

인간 vs 에이전트 — 분업

PROBE는 탐사선입니다. 전투는 하지 않습니다. 인간의 판단이 개입해야 하는 지점은 명확합니다.

🧑‍🔬 인간이 소유
🎯방향 — Identity 명제가 여전히 load-bearing 한가? 최우선 Pillar가 여전히 맞는가?
📋Decision Log 큐레이션 — 논문이 default를 흔들면 해당 Decision 업데이트
🔄맥락 갱신 — Checkpoint마다 해당 P#.md의 Tracked Literature/Decision Log 갱신
💬피드백 루프 — 어떤 스카우트 논문이 실험/Decision을 바꿨는가
🗑️버리기 — 대부분의 논문은 안 중요. 그게 정상.
🤖 에이전트가 소유
🕸️Citation-graph 확장 — Tracked Literature anchor 의미적 이웃
🚫Anti-topic 필터 — Anti-topics 리스트가 배제하는 항목 제거
🔢Scoring — Pillar/Decision fit, novelty, reproducibility, Sim2Real
🌱Cross-pollination — 주기적 인접 분야 강제 픽업
🚨

에이전트는 절대로 context/ 파일(MASTER.md·P#.md)을 편집하지 않습니다. 리포트 안에서 수정 제안만 합니다. 실제 반영은 사람이 결정합니다.

On-demand 모드 — 슬래시 커맨드

정기 스카우트가 outward로 새 논문을 찾는다면, 이 모드들은 인간이 이미 관심을 가진 특정 한 편을 깊이 파거나(analyze-paper), 이미 쌓인 DB를 가로질러 합성합니다(hypothesize). 스케줄링 없이 로컬/웹 세션에서 호출합니다. 모든 로직은 .claude/prompts/<name>.txt에 있고, /<name> 래퍼는 그 파일을 읽어 실행할 뿐입니다.

직접 호출하는 커맨드는 두 개입니다.

/analyze-paper <id | url | pdf>

인간이 이미 관심을 가진 한 편(보통 context/P#.md §5의 pinned/anchor 논문 중 아직 내재화하지 못한 것)을 읽고 한글 deep-dive를 남깁니다.

본문 획득
arxiv.org/abs → /html → ar5iv → abstract-only, 획득 레벨을 문서 헤더에 기록
출력
analysis/<id>/analysis.md — 매 실행 덮어쓰기
구조
(A) 중립 요약 + (B) Decision Log 기반 decision-grade 함의

/hypothesize <P0..P5 | D# | D#-D#>

누적된 analysis/<id>/ deep-dive들을 한 pillar/decision 범위로 가로질러 읽어, Decision Log(D1–D32)에 대한 tension을 채굴하고 순위화·반증가능한 가설을 합성합니다. 읽기 전용 — 실험을 실행하지 않습니다.

옵션
--seed "<아이디어>"(top-down 주입) · --compare-only · --top-k N
사전조건
analysis/README.md 존재 + 범위에 묶인 분석 ≥3편 (미달이면 정직하게 중단)
출력
hypotheses/<slug>/hypotheses.md — D#-앵커 가설 + 합의·불일치 매트릭스 (모두 inferred/unverified)
💡

이 모드들은 스케줄된 루틴이 아닙니다. 필요할 때 직접 호출하세요. /analyze-paper의 full-text 획득에는 세션 환경에 arxiv.org / ar5iv.labs.arxiv.org / export.arxiv.org 허용이 필요합니다(Stage 3와 동일한 Custom allowlist).

출력 예시 — Scouting Report의 모양

모든 산출물은 docs/style.md의 단일 형식 규칙을 따릅니다. 이모지는 섹션/서브섹션 헤더에만 — 본문 인라인 금지. 스카우트 리포트 본문은 개조식(명사형 종결), analysis 딥다이브는 합니다/됩니다 체. 논문 제목/config·코드 이름/수식/P#·D#·CP# 태그/arXiv 링크/이모지/anchor는 verbatim.

🥇Paper N — PRIORITY ★★★최우선 — 즉시 행동
🥈Paper N — PRIORITY ★★읽고 결정에 반영

논문 한 편당 필수 4섹션

### 🎯 (a) P# / D# touched
어느 Pillar / Decision 을 건드리는가

### ✨ (b) What is genuinely new
이미 알려진 work 대비 무엇이 새로운가

### ⚙️ (c) Decision implication
"이 논문이 맞다면 다음 주 내 학습·평가 파이프라인에서
 무엇을 바꿔야 하는가" — 구체적 config 키, 하이퍼파라미터,
 메트릭, loss term. 모호하면 실패.

### ⚠️ (d) Failure mode to probe first
가장 먼저 확인할 실패 시나리오

Scoring (0–3 scale, 4축)

축질문
Relevance 어느 P# / D# 을 건드리는가?
Novelty 진짜 새로운가, tracked work에 대한 delta인가?
Reproducibility 코드 / 데이터 / 하드웨어 상세가 있는가?
Sim2Real 실기 robot 증거가 있는가, sim-only인가?
📐

"모든 축에서 ≥ 2"가 게이트. 통과 못 하는 논문은 패딩하지 않고 솔직하게 0편이라고 보고합니다.

운영 노하우

초반에 반드시 나타나는 문제 3가지

증상원인처방
추천 논문이 Anti-topic에 가까움 Anti-topics 목록이 느슨함 context/P#.md §5 — 더 공격적으로 구체화 ("primary task가 locomotion인 모든 논문")
Decision implication이 generic ("DR range 넓혀야 함") 프롬프트가 약함 scouting.md에 "구체적 config 키 / 하이퍼파라미터 / 메트릭을 지목하라" 강화
같은 논문이 두 주 연속 추천됨 이전 2주 로그를 안 읽음 프롬프트의 read-only "last 2 weeks of scouting/" 참조가 살아 있는지, 파일이 존재하는지 확인
루틴은 돌았지만 PR이 비어 있다 / 모든 curl이 실패 아웃바운드 네트워크 정책 Network access = Custom 으로 export.arxiv.org / arxiv.org / api.semanticscholar.org 허용
Semantic Scholar가 키를 보낼 때만 403 무효/미승인 키 SEMANTIC_SCHOLAR_API_KEY 환경변수 제거 → keyless 200 OK

Echo chamber 방지

Citation-graph만 쓰면 본인 관심사 주변에서만 맴돕니다. context/MASTER.md의 Cross-pollination 로테이션 섹션이 이를 막습니다. 주기적으로 인접 분야(접촉 최적화, FEM 시뮬레이션, 촉각 신경과학 등)에서 강제로 1편을 픽업하는 것이 의외로 가장 가치 있는 발견의 소스입니다.

관련 프로젝트 — 하나의 연구 루프

probe → nexus → observer는 하나의 루프입니다. PROBE가 아이디어를 발굴하고, NEXUS가 실험을 로깅하고, OBSERVER가 정책을 평가합니다.

🛸

probe (여기)

Research scouting — 위 두 프로젝트가 "무엇을 실험할지"를 결정하기 전의 upstream. 정기 스카우트 3 ~ 5편 / on-demand 분석.

🔷

nexus

Centralized RL experiment hub — MLflow + TensorBoard dual logging, air-gapped GPU 서버 SCP sync.

👁️

observer

Automated evaluation pipeline — multi-view recording, failure-mode classification, checkpoint ranking.

🔁

PROBE가 발굴한 아이디어가 NEXUS에서 실험되고, OBSERVER로 평가됩니다. 세 프로젝트가 같은 결정 루프의 세 페이즈입니다.
