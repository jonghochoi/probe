## 🥇 논문 1

**What Makes a VLA Reactive? A Study of Execution Strategies for Dynamic Manipulation**
[arXiv:2611.15491](https://arxiv.org/abs/2611.15491) · Zhuoyue Li 외 4인 · arXiv preprint · source: keyword-sweep

**점수 11/15** · R3 · N2 · M3 · Real3 · Repro0 — 초록·arXiv comment·본문 모두 코드 저장소나 공개 약속 없음

### (a) 관련 Pillar / 질문

[![P6](https://img.shields.io/badge/P6-e4d8f5.svg)](#ref-P6) / [![D0BZ](https://img.shields.io/badge/D0BZ-d97706.svg)](#ref-D0BZ) [![D1MZ](https://img.shields.io/badge/D1MZ-d97706.svg)](#ref-D1MZ)

### (b) 논문 요지

- 움직이는 물체에서 VLA 반응성을 정하는 실행 요인 비교
- **문제** — 물체가 움직이면 VLA가 낸 행동 청크가 실행되기 전에 낡아 버리는 문제
  - 짧은 실행 지평은 재계획을 늘리지만 추론 수요가 커지고 청크 사이 불연속이 생길 수 있음
  - 관측 신선도, 연산 비용, 실행 안정성 사이의 균형이 필요
- **기존 한계** — 원문에 대비 대상 언급 없음
  - 도입부는 더 빠른 행동 생성, 비동기 실행, 궤적 연속성, 시간 정보를 각각 다룬 선행 연구를 나열할 뿐 어느 하나의 한계를 지목하지 않음
- **핵심 방법** — 사전학습 π0.5 하나를 고정해 실행 파이프라인 요인을 바꿔 가며 비교하는 연구
  - **평가 환경** — 동적 시뮬레이션 벤치마크 두 개(DOM, DOMINO)와 실물 동적 과제 세 개
  - **조작 변수** — 예측·실행 지평, 동기와 비동기 추론, 행동을 더 일찍 내놓는 방법과 청크를 연속으로 잇는 방법, 모션 단서와 잠재 공간 강화학습(DSRL)을 통한 정책 적응
- **차별점** — 원문에 대비 대상 언급 없음
  - 새 방법 제안이 아니라 실행 지평, 스케줄링, 궤적 연속성의 효과를 한 백본 위에서 나란히 측정하는 데 있음
- **핵심 기여** — 세 질문에 답하는 비교 결과
  - 최적 예측 지평은 약 1초, 최적 실행 지평은 체크포인트에 따라 달라짐
  - 짧은 지평은 비동기 실행에서 더 큰 이득
  - 궤적을 연속으로 유지하는 방법이 지연만 줄이는 방법보다 우수
  - 정책 적응은 지목된 실패를 고치지만 컨베이어 과제에서는 실행 지평 변경이 같은 정도의 이득
  - 실물 Franka Panda 세 과제(움직이는 컵 놓기, 구르는 캔 잡기, 컨베이어 집기)를 설정당 15–20회 시행으로 비교
- **가치** — 반응성이 정책만이 아니라 실행 파이프라인에도 달려 있어 둘을 함께 평가해야 한다는 기준 제시

### (c) 시사점

- 청크 연결과 실행 주기 중 무엇이 효과를 내는지 같은 백본에서 가른 비교 근거
- **연속성 대 지연 단축** — 지연만 줄이는 방법보다 연속성 유지가 앞선다는 결과로, 청크 경계 처리 선택의 근거
- **지평 설정** — 비동기일수록 짧은 지평이 유리해, 실행 주기 설정을 체크포인트별로 다시 잡을 필요
- **도입 비용** — 새 학습 없이 지평과 실행 방식만 바꿔도 컨베이어 과제에서 정책 적응과 비슷한 이득

### (d) 먼저 확인할 점

- 저자 명시 한계 — 결과는 π0.5 기반 적응에 한정되고 과제 수가 적음
- 실물 비교는 설정당 15–20회 시행이라 작은 차이는 분산에 묻힐 가능성
- 모두 그리퍼 팔의 동적 과제, 다지 손의 접촉 단계에서도 같은 순위가 유지되는지는 별도 확인 필요
- 코드 저장소나 공개 약속 없음

## 🥈 논문 2

**VLALagBench: Understanding When and Why VLA Inference Latency Matters**
[arXiv:2611.03103](https://arxiv.org/abs/2611.03103) · Qi Wen 외 13인 · arXiv preprint · source: keyword-sweep · 코드 공개

**점수 11/15** · R3 · N2 · M2 · Real2 · Repro2 — arXiv comment "code: https://github.com/codestrongestx/vla-lag-bench"

### (a) 관련 Pillar / 질문

[![P6](https://img.shields.io/badge/P6-e4d8f5.svg)](#ref-P6) / [![D1MZ](https://img.shields.io/badge/D1MZ-d97706.svg)](#ref-D1MZ)

### (b) 논문 요지

- VLA 추론 지연이 성공률을 얼마나 깎는지 재는 벤치마크
- **문제** — 추론 지연과 과제 성공률의 관계가 거의 알려지지 않은 문제
  - VLA가 물리 세계의 변화를 따라가려면 실시간 응답이 필요
- **기존 한계** — 지연이 성공으로 이어지는 경로를 재지 못한 기존 연구들
  - **VLA-Perf** — 10Hz와 100Hz를 허용·고성능 기준점으로 쓰되 이 주기가 과제 성공으로 어떻게 환산되는지 평가하지 않음
  - **Realtime-VLA 계열** — 추론·실행 속도를 개선했으나 떨어지는 펜 잡기 같은 제한된 과제에서만 이득을 보임
  - **LIBERO, RoboCasa** — 정적 환경이라 진화하는 환경에서의 지연 영향을 보여 주지 못함
  - **DOM, MoveBench, ReflexBench** — 지연을 생략하거나 특정 하드웨어에 묶인 지연을 쓰거나 정책·과제가 제한적
- **핵심 방법** — 지연을 통제 변수로 주입하는 벤치마크와 성공률 예측 모델
  - **다섯 요인** — 과제 유형(움직이는 물체 잡기, 움직이는 용기에 놓기, 움직이는 면에 놓기, 움직이는 관절 물체 조작), 물체 속도, VLA 정책(π0.5, GR00T N1.7, MolmoAct2), 실행 모드(동기와 여러 비동기), 추론 지연 수준
  - **환경** — 주 벤치마크는 MuJoCo, 결과 검증에 Isaac Sim과 실물 로봇
  - **예측 모델** — 적은 보정 측정으로 지연·실행 모드·실행 지평별 성공률을 추정해 시스템별 설정을 고름
- **차별점** — 지연 수준, 물체 속도, 정책, 실행 모드를 한 틀에서 교차해 지연 민감도의 원인까지 분해
  - 낡은 관측과 동기 추론 중 로봇 정지, 두 경로로 성공률 손실을 설명
- **핵심 기여** — 벤치마크, 발견, 예측 모델
  - 시뮬레이션에서 0.1 m/s 물체에 100 ms 지연이 한 과제 성공률을 71.5%에서 40.5%로 낮추고 다른 과제는 86.5%에서 74.0%로 유지
  - 낡은 관측은 정밀 조작 과제를, 로봇 정지는 연속 동작 과제를 해침
  - 비동기 실행은 정지를 없애 이득을 주지만 추론 요청 빈도가 늘어나는 대가
  - 정책마다 지연 민감도가 달라 지연과 과제별 최고 정책이 바뀜
  - 성공률 예측 모델의 제곱근 평균 제곱 오차 5.7–7.8%
- **가치** — 추론 시스템의 지연과 처리량에 맞춰 VLA 알고리즘 설정을 고르는 알고리즘·시스템 공동 설계의 기준점 제공

### (c) 시사점

- 정책 주기 루프가 무엇을 버티고 못 버티는지 지연 수준별로 잰 공개 기준점
- **지연 한계선** — 100 ms 지연이 움직이는 물체 과제 성공률을 크게 깎는 수치, 센싱과 행동 주기 설정의 하한 근거
- **비동기 비용** — 정지를 없애는 대신 추론 요청이 늘어나는 맞교환의 정량
- **도입 비용** — 코드 공개로 바로 재현 가능, 보정 측정 몇 점으로 설정 선택 가능

### (d) 먼저 확인할 점

- 주 결과는 MuJoCo 시뮬레이션, 실물은 Appendix F의 느린 표적(0.02와 0.05 m/s) 검증에 한정
- 반복 시드나 분산 진술 없음, 비교는 요인 연구 중심
- 평가가 그리퍼 기반 이동 물체 과제, 접촉이 빠르게 바뀌는 다지 손 과제로의 이전은 별도 확인 필요
- 두 번째 버전(v2) 기준 본문 확인

## 🥉 논문 3

**Retiming Robot Demonstrations with a Learned Speed Prior**
[arXiv:2610.32676](https://arxiv.org/abs/2610.32676) · Seungyong Moon 외 9인 · arXiv preprint · source: citation-graph

**점수 10/15** · R3 · N2 · M2 · Real3 · Repro0 — 초록·arXiv comment·본문 모두 코드 저장소나 공개 약속 없음

### (a) 관련 Pillar / 질문

[![P6](https://img.shields.io/badge/P6-e4d8f5.svg)](#ref-P6) / [![D3MR](https://img.shields.io/badge/D3MR-d97706.svg)](#ref-D3MR)

### (b) 논문 요지

- 손에 쥔 그리퍼의 속도로 시연을 재타이밍하는 속도 사전분포
- **문제** — 시연 속도가 과제가 아니라 조작자와 수집 장비로 정해져 정책이 느린 속도를 그대로 물려받는 문제
  - 원격조작은 손에 쥔 그리퍼보다 느리고, 초보 조작자는 주저하거나 멈춤
- **기존 한계** — 시연을 재타이밍하거나 실행을 가속하는 기존 방법이 원래 시연 타이밍에 머무름
  - 과제 요구, 외부 속도 명령, 로봇 한계를 기준으로 원래 타이밍을 조정하는 방식
  - 더 빠르게 움직이는 시연자의 속도를 배워 오는 방법은 드묾
  - 관절 PD 제어는 한계 안에서 계획하지 않아 빠른 목표에서 추종 지연이나 안전 정지가 발생
- **핵심 방법** — 빠른 시연자의 경로별 속도를 예측하는 사전분포와 그 속도를 한계 안에서 실행하는 제어기
  - **속도 사전분포** — 끝점 경로의 국소 형태, 손목 카메라 영상, 과제 지시를 입력으로 경로 각 부분의 속도 분포를 예측, 원격조작 DROID와 손 그리퍼 FastUMI-100K를 종류 라벨과 함께 한 번에 학습
  - **재타이밍** — 분포의 분위수가 경로는 두고 타이밍만 바꾸는 시계, 중앙값 시계로 π0.5 DROID 정책을 미세조정하고 더 높은 분위수 속도를 템포 채널로 함께 예측
  - **실행 제어기** — 예측 속도를 상한으로 보고 로봇 한계가 걸리는 곳에서만 감속, 새 청크가 오면 위치·속도·가속도 연속성을 지키며 이어 붙임
- **차별점** — 같은 경로를 복사하지 않고 빠른 시연자의 속도를 모델로 배워 다른 경로의 시연에도 적용
  - 데이터 자신에서 가속 신호를 뽑는 방식과 달리 학습된 하나의 사전분포가 한 코퍼스의 모든 과제를 덮음
- **핵심 기여** — 사전분포, 제어기, 시뮬레이션과 실물 결과
  - RoboLab 120개 과제에서 같은 가속비의 균일 가속 정책보다 성공률이 높고, 2.4배에서 저크 52% 감소
  - 가장 빠른 DROID 에피소드만 학습한 정책은 속도가 1.5배인데도 실행은 1.07배 빠를 뿐
  - 실물 컵 쌓기 3.50초, 기본 정책 6.02초 대비 1.72배 빠르고 30회 중 29회 성공, 가장 짧은 4분의 1 에피소드만 학습한 정책은 30회 중 9회
  - 제어기를 관절 PD 대신 쓰면 기록 타이밍 정책도 타월 접기 성공률이 13%에서 97%
- **가치** — 사람 속도를 재타이밍 목표로 삼고 로봇 한계를 지키며 실행하는 경로 제시

### (c) 시사점

- 실행 속도를 데이터 단계의 학습된 시계로 정하고 제어기로 한계를 지키는 사례
- **빠른 데이터만으로는 부족** — 빠른 에피소드만 학습하면 실물 성공이 9/30으로 떨어져, 재타이밍과 전체 데이터 활용의 조합이 필요하다는 근거
- **실행 제어기** — 새 청크를 위치·속도·가속도 연속으로 잇는 제어기가 정책 변경 없이 성공률을 올린 측정
- **도입 비용** — 속도 사전분포 학습과 손에 쥔 그리퍼 시연 수집이 필요하고 코드 비공개

### (d) 먼저 확인할 점

- 반복 시드나 분산, 한계 진술 없음
- 4.2배 빠르다는 SAIL 대비 비교는 저자가 다른 논문 수치와 견준 것이라 설정이 다를 수 있음
- 실물 과제가 컵 쌓기, 타월 접기 등 그리퍼 기반, 접촉이 많은 다지 손 과제에서 같은 속도 이득이 유지되는지는 별도 확인 필요
- 코드 저장소나 공개 약속 없음, 프로젝트 페이지만 있음
